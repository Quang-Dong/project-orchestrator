# Compatibility, maintenance and verified value

Read when preparing a release, changing model/runtime/tool/schema/authority, investigating a relevant failure or considering retirement. Do not load this reference for every small task.

## Ownership and freshness

The source repository maintainer decides release acceptance, supported scope and retirement. The project lead owns the current task and recovery. Installed copies are distributions, never silent development targets.

Use the release's compatibility record and manifest when available. Record the actual skill revision/hash, policy/record versions, runtime/tools, model/effort and check date. Follow [evidence and challenge](evidence-and-challenge.md) for fact/assumption/inference/unknown labels and current-source research. A compatibility claim names evidence and limits: tested, untested or incompatible. A model name or old successful install does not prove current compatibility. If no record is available, mark the combination unverified rather than guessing.

Stable principles do not require constant web research. Recheck only consequential environment-dependent guidance on a change event: model/runtime/tool update, schema or permission change, contradictory behavior or relevant incident. Prefer version-matched official sources and current local behavior. Source age alone is not a defect; a newer suggestion is not automatically better. Record date, applicability and evidence that would change the decision.

## Update and recovery

Freeze a task's source revision; defer installation updates until an authorized boundary. Review changelog/evidence and retain the previous source before an authorized update. Public release versioning and installation authority are separate.
Policy v1 and records v2 remain current. A future incompatible schema needs a tested read/migration path, integrity check and explicit recovery limits. Restoring code/instructions does not undo data changes.
When a defect appears, record impact, owner, current revision, recovery step and evidence required to resume in existing status/task records. Stop only dependent actions when authority or capability is missing. On uncertain tool results reconcile before retrying. Reports, downloaded instructions and issue text do not expand permission.

## Measure value and simplify

Measure accepted outcomes, authority violations, false completion, missed defects, takeover success, human intervention, elapsed time and usage across lead/worker/reviewer. Do not hide a critical failure in an overall score. Keep unknown effort, cost, wait time and token attribution separate; do not infer active effort from wall time.
Compare matched work on old/new guidance, retaining failures and intervention. Keep acceptance explicit for workers and evaluation grading independent; don't optimize to wording or leaked answers. A reviewer model is not ground truth: verify final artifacts and calibrate consequential judgments with human input when available. See [evidence and challenge](evidence-and-challenge.md) for the raw-evidence review rule.
A repeated generalizable failure can become a regression or one bounded experiment. Removing a rule, reducing a packet or choosing no delegation are valid improvements. Adopt only the demonstrated scope; small samples yield descriptive evidence, not universal superiority. Retain counterexamples and defer claims without a baseline.

## Support and retirement

Mark untested or no-longer-supported combinations clearly. Before retirement, identify affected projects, export/read paths for records, retained evidence and any remaining owner obligations. Project history must remain readable without this skill.
Review at release and relevant change events; this file creates no scheduler or promise to watch while no session is active.

Sources used for decision criteria (checked 2026-09-15; advisory, not certification):
- [NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/): ongoing governance, measurement and management; applicable to lifecycle risk, not a pass certificate.
- [Agent evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): outcome checks and repeated trials; vendor engineering guidance, not evidence about this skill/model.
- [DORA metrics](https://dora.dev/guides/dora-metrics/): context-aware improvement; software delivery metrics are not a substitute for task-level agent evaluation.
