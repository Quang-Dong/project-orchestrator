Cross-cutting tension: the entrypoint description emphasizes session coordination and can miss consequential solo product work. Broaden routing without making every small edit traverse nine processes. Keep design and outcome quality mandatory while optimizing time, resource use and maintenance cost within those conditions.

Policy v1, records v2, scripts/CLI, dependencies, explicit/Auto confirmation and adaptive effort rules are outside this change. The authorized delivery is a normal commit/push and metadata update to the existing PR; merge, release and installed-copy updates are excluded.

## One linked fictional walkthrough

This is an author-inspected scenario with scripted conditions, not a running application or evidence of demand. Every product observation below is hypothetical.

1. **Request and authority:** a fictional room-booking tool is asked to add automatic confirmation emails because users are unsure whether a booking saved. The task is solo, permits a local candidate, and excludes release/contact. Product guidance separates the proposed email mechanism from uncertainty about saved state; no usage baseline is assumed. The smallest initial step is inspection of the existing save journey and supplied fictional error cases.
2. **Requirements and journey:** suppose the authorized product decision selects clear save feedback instead of email for this increment. The contract says only the creator can edit, successful save is durable, and a failed save preserves the draft. Examples cover a successful transition, denied edit leaving data unchanged and interrupted save with recoverable input. If conflicting permission rules are discovered, dependent edits wait. Keyboard focus and retry feedback are part of the changed UI acceptance.
3. **Design:** retain the existing application and persistence boundary; name the authoritative booking state, permitted writer, request/result contract and failure path. Walk an evidenced future change such as adding one booking field through the affected modules, then an interrupted write through the UI and storage invariant. No load/team evidence justifies a queue or separate service. A design walkthrough proposes the check; it is not a passing check.
4. **Implementation and diagnosis:** inspect actual callers, versions and conventions; exercise the smallest real save path early. Suppose isolated checks pass but the caller mishandles a rejected write. Compare successful/rejected boundary results to distinguish mapping from storage failure before editing. After a supported repair, rerun the original rejection and successful-save cases plus the affected permission check. A third guess after two failed repairs requires evidenced reassessment or a stopped handoff.
5. **Evidence and acceptance:** attach results only if those checks actually run on the candidate. Include the running recovery/keyboard journey and persistent-state checks required by the contract; keep skips or unavailable checks open. Solo self-inspection cannot close the independent persisted-data/security review gate. Even a technically accepted slice would not demonstrate user value without relevant feedback.
6. **Operations and handoff:** release remains unauthorized. The current handoff names candidate revision, owner, actual checks, unknowns and pending independent review, release and user-value questions. If a later release requires a migration, verify real data recovery separately from code rollback. A future authorized user review supplies the feedback event; no schedule or outreach is created. Continue/adjust/defer/stop depends on that evidence. A caller defect stays in code/tests; only a supported general decision failure warrants a bounded skill rule.

The chain preserves the same rule examples and acceptance conditions across design, implementation, proof and handoff. It shows how the instructions connect; it does not establish their practical effectiveness.
